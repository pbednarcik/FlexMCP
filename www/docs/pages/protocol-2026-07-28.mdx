# Protocol Version 2026-07-28

The `2026-07-28` revision turns MCP from a stateful, bidirectional protocol into
a stateless request/response one. Every request is self-describing, so any
request can land on any server instance behind a plain round-robin load
balancer.

mcp-go speaks this revision and every earlier one, deciding which to use per
connection. **Existing code keeps working unchanged**: if you do nothing, your
server continues to serve older clients exactly as before, and gains support
for newer ones.

## What changed

| | Before `2026-07-28` | From `2026-07-28` |
| --- | --- | --- |
| Connecting | `initialize` / `notifications/initialized` handshake | No handshake. Each request carries its version, identity, and capabilities in `_meta`. |
| Discovery | The `initialize` response | The [`server/discover`](#discovery) RPC, which servers must implement and clients may skip |
| Sessions | `Mcp-Session-Id` header, terminated with `DELETE` | Removed. Servers ignore the header and answer `GET` and `DELETE` with `405`. |
| Asking the user something | Server-initiated requests over a held-open stream | [Multi round-trip requests](#multi-round-trip-requests) |
| Change notifications | A standalone `GET` SSE stream | [`subscriptions/listen`](#subscriptions), with opt-in filters |
| Resumability | `Last-Event-ID` replay | Removed. Re-issue the request with a new ID. |
| Routing | Parse the JSON body | The `Mcp-Method` and `Mcp-Name` headers |
| Caching | — | `ttlMs` and `cacheScope` on list and read results |
| Removed RPCs | — | `ping`, `logging/setLevel`, `resources/subscribe`, `resources/unsubscribe` |

## Servers

A server built the usual way serves both eras on one endpoint:

```go
srv := server.NewMCPServer("my-server", "1.0.0",
    server.WithToolCapabilities(true),
)

http.ListenAndServe(":8080", server.NewStreamableHTTPServer(srv))
```

The era is decided per request, from the protocol version the request declares.
Nothing about how you register tools, prompts, or resources changes.

### Pinning to earlier revisions

Deployments that depend on protocol-level session state — per-session tools, for
example — can advertise only the revisions that provide it:

```go
server.NewStreamableHTTPServer(srv,
    server.WithStreamableHTTPProtocolVersions(mcp.LegacyProtocolVersions()...),
)
```

Modern clients then receive an `UnsupportedProtocolVersionError` naming the
versions you do support, and negotiate down automatically.

### Cache hints

List and read results carry a freshness hint from this revision on. The default
asks clients to revalidate every time, which preserves earlier behaviour:

```go
server.NewMCPServer("my-server", "1.0.0",
    // Clients may reuse tool and prompt catalogs for a minute.
    server.WithCacheHints(60_000, mcp.CacheScopePublic),
    // Resource contents are user-specific, so no shared cache may hold them.
    server.WithMethodCacheHints(mcp.MethodResourcesRead, 5_000, mcp.CacheScopePrivate),
)
```

Hints are only emitted to clients using `2026-07-28` or later.

### Multi round-trip requests

A tool that needs something from the user mid-call used to send the client a
request over a held-open stream. That cannot work on a stateless protocol, so
the server now says what it needs and the client retries the call with the
answers attached.

Write the handler once, and it works for clients of either era:

```go
srv.AddTool(mcp.NewTool("deploy"), func(ctx context.Context, req mcp.CallToolRequest) (*mcp.CallToolResult, error) {
    // On the retry, the client's answer is waiting for us.
    if answer := server.ElicitationResponse(req.Params.InputResponses, "confirm"); answer != nil {
        if answer.Action != mcp.ElicitationResponseActionAccept {
            return mcp.NewToolResultText("deployment cancelled"), nil
        }
        return mcp.NewToolResultText("deployed"), nil
    }

    // First call: ask, and hand back whatever state we need to resume.
    return server.NewInputRequestBuilder("awaiting-confirmation").
        Elicit("confirm", mcp.ElicitationParams{
            Mode:    mcp.ElicitationModeForm,
            Message: "Deploy to production?",
            RequestedSchema: map[string]any{
                "type":       "object",
                "properties": map[string]any{"ok": map[string]any{"type": "boolean"}},
            },
        }).
        ToolResult(), nil
})
```

`requestState` is opaque to the client and echoed back verbatim, so use it to
carry whatever your handler needs to pick up where it left off. It is the right
place for a continuation token; it is not a place for secrets, since the client
can read it.

The server never asks for what the client cannot answer. Each input request
needs a capability the request declared in its `_meta`: `elicitation` (with
`url` for URL mode), `sampling` (with `tools` when the request carries tools),
or `roots`. A client that did not declare it gets error `-32021` instead,
whose `data.requiredCapabilities` names the set it would need. A client on an
earlier revision cannot answer an input request at all, and the server sends
no requests of its own, so that call fails with
`server.ErrInputRequiresModernClient`.

### Subscriptions

`resources/subscribe` and the standalone `GET` stream are replaced by a single
long-lived request. Clients opt in to specific notification types, and the
server intersects that with what it can actually serve:

```go
srv := server.NewMCPServer("my-server", "1.0.0",
    server.WithToolCapabilities(true),          // enables toolsListChanged
    server.WithResourceCapabilities(true, true), // enables resourcesListChanged; per-resource subscriptions are not served yet
)
```

Your notification-sending code is unchanged. Delivery is opt-in for a modern
client: over HTTP each `subscriptions/listen` request is its own stream; over
stdio and in-process, where one channel carries everything, a client may hold
several streams at once and a broadcast goes out once per stream that asked
for it, each copy tagged with its stream's id in `_meta`. A modern client that
holds no stream receives no broadcast. A client of an earlier revision keeps
receiving them unfiltered, as its revision prescribes.

### Logging

`logging/setLevel` is gone. Clients name a level per request, and a server must
not emit log notifications for a request that did not ask for one.
`SendLogMessageToClient` applies that rule automatically.

## Clients

`Initialize` probes with `server/discover` and falls back to the handshake, so
the same code connects to servers of either era:

```go
c := client.NewClient(httpTransport)
if err := c.Start(ctx); err != nil {
    return err
}

var req mcp.InitializeRequest
req.Params.ClientInfo = mcp.Implementation{Name: "my-client", Version: "1.0.0"}

result, err := c.Initialize(ctx, req)  // result.ProtocolVersion tells you which era won
```

On a modern connection the client adds the required `_meta` and headers to every
request, and neither sends nor stores a session ID.

### Multi round-trip requests

Register the handlers you already would, and `CallTool`, `GetPrompt`, and
`ReadResource` fulfil the server's requests and retry for you:

```go
c := client.NewClient(httpTransport,
    client.WithElicitationHandler(myHandler),
    client.WithMaxInputRoundTrips(5),  // optional; the default is 10
)

// Returns the final result. Any input the server needed was gathered
// and resubmitted along the way.
result, err := c.CallTool(ctx, req)
```

The result you get is the final one: an `input_required` result never reaches
the caller, and a server that keeps asking past the bound fails the call with
`ErrMaxInputRoundTripsExceeded`.

### Subscriptions

```go
stop, err := c.ListenAsync(ctx, mcp.SubscriptionFilter{
    ToolsListChanged:      true,
    ResourceSubscriptions: []string{"file:///config.json"},
}, func(err error) {
    log.Printf("subscription stream ended: %v", err)
})
defer stop()
```

Notifications reach the handlers registered with `OnNotification` as before.

### Pinning to an earlier revision

```go
c := client.NewClient(httpTransport,
    client.WithProtocolVersion(mcp.ProtocolVersion20251125),
)
```

A transport configured with `WithContinuousListening` pins itself
automatically, since that option depends on the `GET` stream this revision
removed.

## Migrating

Nothing is required to adopt the new revision. A few client APIs and
behaviours did change along the way; see [Client changes](#client-changes)
before upgrading a client, and
[Request ids and progress tokens](#request-ids-and-progress-tokens) before
upgrading either side. When you are ready to adopt the new capabilities:

1. **Rewrite server-initiated requests as multi round-trip handlers.** Replace
   `RequestSampling`, `RequestElicitation`, and `RequestRoots` calls with
   `NewInputRequestBuilder`. The result works for old and new clients alike.
2. **Stop relying on protocol-level session state.** Mint an explicit handle
   from a tool and have the model pass it back as an argument. This works
   better than state hidden in the transport, because the model can see the
   handle and thread it between tools.
3. **Replace `Subscribe` with `Listen`** on clients that consume notifications.
4. **Set cache hints** for catalogs that do not change often.
5. **Move off `WithContinuousListening`,** `Ping`, and `SetLevel`, all of which
   degrade to no-ops or local state on a modern connection.

Deprecated features remain functional for at least twelve months under the MCP
[feature lifecycle policy](https://modelcontextprotocol.io/community/feature-lifecycle).

## Client changes

These change what a client sees, whichever revision it speaks. The ones that
need code are marked **(code)**.

### Pagination

- **(code)** `PaginatedParams.Cursor` and `PaginatedResult.NextCursor` are
  `*mcp.Cursor`. A missing `nextCursor` ends a listing; an empty one is a
  cursor, sent on the next request. The `NewList*Result` helpers still take
  an `mcp.Cursor`, where empty means the last page.

### OAuth

- **(code)** PKCE with S256 is on by default, and an authorization server whose
  metadata does not list S256 is refused. `PKCEEnabled` has no effect;
  `PKCEDisabled` turns PKCE off for a server known to lack it.
- **(code)** Hand the redirect's query to `ProcessAuthorizationCallback`, which
  validates `iss` (RFC 9207). `ProcessAuthorizationResponse` refuses a response
  without `iss` from a server that advertises it, and a state is good for one
  response.
- **(code)** A handler used on its own needs `SetBaseURL` before an
  authorization or a token request, and before discovery from the MCP server
  (`ErrResourceUnknown`); discovery and registration through a configured
  `AuthServerMetadataURL` work without it. The transports set it. Every
  authorization and token request names the `resource`: the one the server's
  protected resource metadata declares, or the base URL when there is no such
  metadata. Either must be absolute, with no fragment (`ErrInvalidResource`).
- **(code)** Authorization server endpoints are HTTPS only: metadata fetched
  over `http`, or naming an `http` issuer or endpoint, is refused
  (`ErrInsecureAuthorizationServer`), a local authorization server included.
  Discovery follows a redirect only while the URL it reaches, after the
  HTTP client's own redirect policy, stays on `https`; a token, refresh or
  registration request follows none.
- **(code)** An access token goes only to its own server: with OAuth
  configured, a Streamable HTTP or SSE request follows a redirect only while
  its scheme, host and port stay the same (`ErrRedirectLeavesOrigin`).
- Discovery that gets no answer (a failed or cancelled request, a `5xx` or
  `429`) returns the error and tries again on the next call; the default
  endpoints stand in only for metadata that is not there. Without protected
  resource metadata, metadata found under the MCP server's path must name
  that URL as its issuer or is not used, and the metadata at the host's root
  must name the origin.
- Authorization server metadata must name its `issuer` (RFC 8414); metadata
  without one is not used, wherever it came from.
- Client credentials belong to one authorization server: `ClientIssuer`, or
  else the first one they are used with. Another is refused
  (`ErrClientRegisteredElsewhere`). Without `ClientIssuer`, configured
  credentials go to the first authorization server discovery names; set it, or
  `AuthServerMetadataURL`, when they are for a known one. Store credentials
  under `GetClientIssuer`. Registering again replaces the client ID and the
  secret.
- Saved tokens record the server and the issuer they are for (`Token.Resource`,
  `Token.Issuer`), and neither the token nor its refresh token is sent anywhere
  else. `RefreshToken` refuses when the token store cannot be read. A
  transport's requests carry no token while its handler is pointed at another
  server. A token without the record, as one your code stores itself, is used
  as before, but its refresh token goes only to the issuer `ClientIssuer`
  names; without `ClientIssuer` the expired token asks for a new
  authorization. A token store that keeps `Token.Issuer` keeps refreshing.
- A change of `SetBaseURL` abandons an authorization that is pending or
  starting, and a code is redeemed only for the resource and at the issuer it
  was obtained for (`ErrResourceChanged`, `ErrIssuerMismatch`): one whose
  callback is already being redeemed completes only if the handler names that
  resource and issuer again. A callback handled by another handler instance
  (`SetExpectedState`) has no resource recorded, so it is redeemed for the one
  that handler names.
- A 403 with `insufficient_scope` is an `AuthorizationRequiredError`, like a
  401. One challenge is acted on: `Bearer` before `DPoP`. Its scopes are the
  refused operation's and are replaced by the next challenge.
- Dynamic client registration states an `application_type`: `web` for an
  `https` redirect, `native` for any other.
- Without a `resource_metadata` pointer, protected resource metadata is asked
  for at the MCP server's path, then at the host's root, before endpoints are
  guessed. An authorization endpoint's own query is kept in the
  authorization URL.
- A token that carries a refresh token is renewed in the last 10 seconds of
  its life, at most half of it; a failed early refresh keeps the token while
  it is valid. A refresh token the authorization server refused with an OAuth
  error is not sent again; a network failure, a 5xx or 429 status, or a
  `server_error` or `temporarily_unavailable` error is retried.
- A token response without an `access_token`, or with a `token_type` other
  than Bearer, is refused (`ErrInvalidTokenResponse`) and nothing from it is
  saved; one naming no type is taken as Bearer. A registration response
  without a `client_id` is refused (`ErrInvalidRegistrationResponse`) and the
  credentials stay as they were.

### Results and capabilities

- A `resultType` the client does not know is an error, not a complete result.
  `task` is accepted only on `tools/call`, on this revision, when the client
  declared `extensions["io.modelcontextprotocol/tasks"]`; the task is then in
  `CallToolResult.Task`.
- Without a `clientInfo` of your own, the client names itself `flexmcp` at the
  version it was built with.
- Roots must be `file://` URIs. On this revision `listChanged` is not declared
  and `RootListChanges` sends nothing.
- A tool call refused for a stale `Mcp-Param-*` header lists the tools again
  and retries once. A complete `IterTools` walk replaces the tool cache, as
  `ListTools` does; one stopped early merges what it read.
  `WithInvalidToolHandler` is told of each tool excluded for invalid
  `x-mcp-header` annotations.
- `WaitForTask` also returns a task in `input_required`, which only the
  requestor can move on.
- A server request the client cannot serve is answered with the code its
  failure calls for: an unknown method, or a feature with no handler,
  `-32601`; params that do not decode or validate `-32602`; anything else
  `-32603`. A handler's panic is answered `-32603` rather than ending the
  process.

### Transport

- Cancelling a request on an earlier revision over Streamable HTTP sends
  `notifications/cancelled`.
- An SSE `endpoint` event must keep the connection's scheme, host and user
  info: an `https` connection does not take an `http` endpoint.
- On this revision a `404` with a JSON-RPC body is that error, not the end of a
  session.
- A failed `initialize` establishes no session, and a `4xx` to it with a
  JSON-RPC body is that error, not a sign of an HTTP+SSE server.
- A request the server sends over SSE is not taken for the response to a
  client request with the same id. The SSE transport serves no server
  requests: it answers `ping` with an empty result and any other method with
  `-32601`; `Close` abandons an answer still being posted.
- Over Streamable HTTP, a POST's answer is the response carrying its request's
  id, or an error with a null id, whatever the HTTP status. A JSON answer to
  another id is an error; on a stream such a response is skipped, and the
  stream is read on for the request's own. An `initialize` left without its
  answer gives back the session ID its headers carried.
- A server request whose `jsonrpc` member is not `"2.0"` is answered `-32600`
  with its id, on every transport; responses and notifications are taken as
  they come.
- Over stdio, `Start` after `Close` is `ErrTransportClosed` and a send before
  `Start` is `ErrTransportNotStarted`. `Close` cancels the handlers of server
  requests. A send queued behind a write the child is not reading gives up
  with its context. An answer that names a pending request but cannot be
  decoded fails that request. A notification handler may set the handler, but
  must not wait for a request's answer, which the read loop delivers.

## Request ids and progress tokens

These apply to servers and clients alike, whichever revision they speak.

- **(code)** A numeric request id reaches your code as an `int64`, or a
  `json.Number` for an integer past int64, where it was a `float64`: the `id`
  passed to hooks, `RequestId.Value()`, `SubscriptionStream.ID` and
  `WithSubscriptionID`. A numeric `progressToken` (`Meta.ProgressToken`,
  `ProgressNotificationParams.ProgressToken`) arrives the same way, and a
  fractional token stays a `float64`. A type switch or assertion on
  `float64` no longer matches.
- A request id is a string or a plain integer literal, never `null`. A request
  with any other id, `1.0`, `1e3`, `1.5`, `true` or an object, is refused with
  `-32600` and a null id, by the server and by a client alike; a message with
  `"id": null` and a method is such a request, not a notification. A response
  whose id a client cannot read answers nothing it can name and is dropped.
- A message that is neither a request, a notification nor a response, such
  as one with no method or one whose method is not a string (`null`, `5`),
  gets `-32600`, carrying its id when that could be read, and over Streamable
  HTTP a `400`; `-32700` is only for text that is not JSON.
- A message is a request or a notification by its `method` member being
  there, not by its value: `"method": ""` asks for a method named `""`, which
  is not found (`-32601`), on the server and on a client alike, and is never
  taken for a response.
- A notification is never answered, not even one whose params cannot be read;
  over Streamable HTTP such a notification is refused with `400`.
- A response the server receives is never answered, whatever its id, and a
  `null` result or error still makes one; a message with a method member is
  a request, whatever it carries besides. Over Streamable HTTP on this revision,
  where the server sends no requests, a POSTed response, or an id alone, is
  refused with `400`; earlier revisions accept an id alone with `202`, as an
  empty response.
