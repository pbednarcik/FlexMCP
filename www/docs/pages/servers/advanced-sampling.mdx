# Sampling

Learn how to implement MCP servers that can request LLM completions from clients using the sampling capability.

:::warning[Sampling is deprecated]
Protocol version 2026-07-28 deprecates sampling: new servers should not adopt it, and existing ones should call an LLM provider's API directly instead. It may be removed from the first protocol revision released on or after 2027-07-28. This page is for servers that keep sampling for compatibility with the clients that still offer it.
:::

## Overview

Sampling allows MCP servers to request LLM completions from clients, enabling bidirectional communication where servers can leverage client-side LLM capabilities. This is particularly useful for tools that need to generate content, answer questions, or perform reasoning tasks.

:::info[User Consent Required]
Per the [MCP specification](https://modelcontextprotocol.io/specification/2025-06-18/client/sampling#user-interaction-model), clients **SHOULD** implement human-in-the-loop approval for sampling requests.

When you request sampling from a client:
- The user will typically be prompted to review and approve your request
- The user may modify your prompts before sending to their LLM
- The user may reject your request entirely
- Response times may be longer due to user interaction

**Design your tools accordingly:**
- Provide clear descriptions of why sampling is needed
- Use descriptive system prompts explaining the purpose
- Expect a rejected request to end the call, with no retry for your tool to handle
- Don't assume immediate or automatic approval

Well-designed sampling requests improve user trust and approval rates.
:::

## Requesting Sampling

The server sends the client no requests of its own. A tool that needs a completion returns a [multi round-trip request](/protocol-2026-07-28#multi-round-trip-requests) instead: `server.NewInputRequestBuilder` collects what the tool needs, `Sample` asks for a completion under a key the tool chooses, and `ToolResult` renders the request as the tool's result. The client runs its sampling handler and calls the tool again with the same arguments and the completion attached, which `server.SamplingResponse` finds under the same key:

```go
mcpServer.AddTool(mcp.Tool{
    Name:        "ask_llm",
    Description: "Ask the LLM a question using sampling",
    InputSchema: mcp.ToolInputSchema{
        Type: "object",
        Properties: map[string]any{
            "question": map[string]any{
                "type":        "string",
                "description": "The question to ask the LLM",
            },
            "system_prompt": map[string]any{
                "type":        "string", 
                "description": "Optional system prompt",
            },
        },
        Required: []string{"question"},
    },
}, func(ctx context.Context, request mcp.CallToolRequest) (*mcp.CallToolResult, error) {
    // Extract parameters
    question, err := request.RequireString("question")
    if err != nil {
        return nil, err
    }
    
    // On the retry, the client's completion waits under the key asked for
    if result := server.SamplingResponse(request.Params.InputResponses, "answer"); result != nil {
        return &mcp.CallToolResult{
            Content: []mcp.Content{
                mcp.TextContent{
                    Type: "text",
                    Text: fmt.Sprintf("LLM Response: %s", mcp.GetTextFromContent(result.Content)),
                },
            },
        }, nil
    }

    systemPrompt := request.GetString("system_prompt", "You are a helpful assistant.")
    
    // First call: ask the client for a completion
    return server.NewInputRequestBuilder("").
        Sample("answer", mcp.CreateMessageParams{
            Messages: []mcp.SamplingMessage{
                {
                    Role: mcp.RoleUser,
                    Content: mcp.TextContent{
                        Type: "text",
                        Text: question,
                    },
                },
            },
            SystemPrompt: systemPrompt,
            MaxTokens:    1000,
            Temperature:  0.7,
        }).
        ToolResult(), nil
})
```

The argument to `NewInputRequestBuilder` is an opaque request state that the client echoes back on the retry, so the tool can resume where it left off; it may be empty. The client can read it, so it is no place for secrets.

## Sampling Request Parameters

`Sample` takes an `mcp.CreateMessageParams`, whose fields control LLM behavior:

```go
params := mcp.CreateMessageParams{
    // Required: Messages to send to the LLM
    Messages: []mcp.SamplingMessage{
        {
            Role: mcp.RoleUser,        // or mcp.RoleAssistant
            Content: mcp.TextContent{   // or mcp.ImageContent
                Type: "text",
                Text: "Your message here",
            },
        },
    },

    // Optional: System prompt for context
    SystemPrompt: "You are a helpful assistant.",

    // Required: Maximum tokens to generate
    MaxTokens: 1000,

    // Optional: Temperature for randomness (0.0 to 1.0)
    Temperature: 0.7,

    // Optional: Stop sequences
    StopSequences: []string{"\n\n"},

    // Optional (2025-11-25): Context inclusion. Omit it; it defaults to
    // "none", and its other values are deprecated. See
    // [Capability Gating](#capability-gating-2025-11-25) below.

    // Optional (2025-11-25): Tools the model may use during generation, and
    // how aggressively the model should reach for them. Only send these when
    // the client advertised `sampling.tools`.
    Tools: []mcp.Tool{ /* ... */ },
    ToolChoice: &mcp.ToolChoice{Mode: mcp.ToolChoiceModeAuto},
}
```

## Capability Gating (2025-11-25)

The 2025-11-25 protocol revision splits sampling into a baseline capability and two opt-in sub-capabilities. From 2026-07-28 the client declares its capabilities on every request, and a handler reads them from `server.RequestProtocolInfoFromContext(ctx)`. Check the [`SamplingCapability`](https://pkg.go.dev/github.com/pbednarcik/flexmcp/mcp#SamplingCapability) there before sending the gated fields:

| Field on `CreateMessageParams` | Required client sub-capability | Sub-capability is `nil` ⇒ |
|--------------------------------|--------------------------------|---------------------------|
| `IncludeContext` (`"thisServer"` or `"allServers"`, both deprecated) | `Sampling.Context` | Omit the field (it defaults to `"none"`) |
| `Tools`                        | `Sampling.Tools`               | Omit the field            |
| `ToolChoice`                   | `Sampling.Tools`               | Omit the field            |

The server enforces the `Sampling.Tools` rows itself: a request for a completion that carries `Tools` or `ToolChoice` fails the call with `mcp.MissingRequiredClientCapabilityError` when the client did not declare `Sampling.Tools`. It does not check `IncludeContext`, so gating that field is up to the handler.

A typical pattern inside a tool handler:

```go
func askLLMWithTools(ctx context.Context, request mcp.CallToolRequest) (*mcp.CallToolResult, error) {
    if result := server.SamplingResponse(request.Params.InputResponses, "answer"); result != nil {
        return mcp.NewToolResultText(mcp.GetTextFromContent(result.Content)), nil
    }

    var sampling *mcp.SamplingCapability
    if info := server.RequestProtocolInfoFromContext(ctx); info != nil && info.ClientCapabilities != nil {
        sampling = info.ClientCapabilities.Sampling
    }

    params := mcp.CreateMessageParams{
        Messages:  []mcp.SamplingMessage{ /* ... */ },
        MaxTokens: 1000,
    }

    // Only attach Tools / ToolChoice if the client opted in.
    if sampling != nil && sampling.Tools != nil {
        params.Tools = []mcp.Tool{ /* ... */ }
        params.ToolChoice = &mcp.ToolChoice{Mode: mcp.ToolChoiceModeAuto}
    }

    // Deprecated: ask for context inclusion only from a client that declared
    // sampling.context.
    if sampling != nil && sampling.Context != nil {
        params.IncludeContext = "thisServer"
    }

    return server.NewInputRequestBuilder("").Sample("answer", params).ToolResult(), nil
}
```

`ToolChoiceMode` accepts three constants:

| Constant | Wire value | Meaning |
|----------|-----------|---------|
| `mcp.ToolChoiceModeAuto`     | `"auto"`     | Model decides (default when `ToolChoice` is omitted). |
| `mcp.ToolChoiceModeRequired` | `"required"` | Model must call at least one tool. |
| `mcp.ToolChoiceModeNone`     | `"none"`     | Tool use is disabled for this request. |

## Message Types

Sampling supports different message roles and content types:

### Message Roles

```go
// User message
{
    Role: mcp.RoleUser,
    Content: mcp.TextContent{
        Type: "text",
        Text: "What is the capital of France?",
    },
}

// Assistant message (for conversation context)
{
    Role: mcp.RoleAssistant,
    Content: mcp.TextContent{
        Type: "text", 
        Text: "The capital of France is Paris.",
    },
}
```

### Content Types

#### Text Content

```go
mcp.TextContent{
    Type: "text",
    Text: "Your text content here",
}
```

#### Image Content

```go
mcp.ImageContent{
    Type: "image",
    Data: "base64-encoded-image-data",
    MIMEType: "image/jpeg",
}
```

#### Tool-Use and Tool-Result Content (2025-11-25)

When sampling with tools is in play, intermediate messages in the conversation
can also carry `ToolUseContent` (the model asked to call a tool) and
`ToolResultContent` (the result of that call) — these flow through the same
`SamplingMessage.Content` field:

```go
// Assistant requesting a tool call
mcp.ToolUseContent{
    Type:  "tool_use",
    ID:    "tu_1",
    Name:  "get_weather",
    Input: map[string]any{"city": "London"},
}

// User-role message carrying the tool's output
mcp.ToolResultContent{
    Type:      "tool_result",
    ToolUseID: "tu_1",
    Content:   []mcp.Content{mcp.NewTextContent("Sunny, 22°C")},
}
```

Use the constructors `mcp.NewToolUseContent` and `mcp.NewToolResultContent` to build these without writing the `Type` discriminator by hand.

## Error Handling

The handler never sees a sampling error: it returns its request, and it is called again only with an answer. Three things end the call instead, and the client gets them as the error from `CallTool`:

- **The client did not declare the capability.** The server answers with `mcp.MissingRequiredClientCapabilityError`, error `-32021`, naming the capabilities the request needed: `Sampling` for any completion, and `Sampling.Tools` for one that carries tools. A client with a sampling handler declares `Sampling`.
- **The client speaks an earlier protocol version.** A version before 2026-07-28 cannot carry a multi round-trip request, and the server sends no request of its own, so the call fails with `server.ErrInputRequiresModernClient` (on the wire, an internal error naming 2026-07-28).
- **The client's sampling handler fails**, for example because the user rejected the request. The client ends the call with that error and does not call the tool again.

To answer a client without sampling with a tool error of your own instead, check before asking:

```go
info := server.RequestProtocolInfoFromContext(ctx)
if info == nil || info.ClientCapabilities == nil || info.ClientCapabilities.Sampling == nil {
    return mcp.NewToolResultError("this tool needs a client that supports sampling"), nil
}
```

## Context and Timeouts

The handler does not wait for the completion: it returns at once, and the client calls the tool again when its handler has answered. A timeout set inside the handler therefore bounds neither the user's approval nor the LLM. The client's context bounds the call as a whole, and `client.WithMaxInputRoundTrips` bounds how many requests one call sends while the server keeps asking (by default 10, the first included).

## Best Practices

1. **Check for the Answer First**: Look for `SamplingResponse` before asking, so the retry finishes the work
2. **Gate Optional Fields**: Send `Tools`, `ToolChoice` and `IncludeContext` only to clients that declared them
3. **Graceful Errors**: Always provide meaningful error messages to users
4. **Content Extraction**: Use helper functions to extract text from responses
5. **System Prompts**: Use clear system prompts to guide LLM behavior
6. **Parameter Validation**: Validate tool parameters before making sampling requests

## Complete Example

Here's a complete example server with sampling:

```go
package main

import (
    "context"
    "fmt"
    "log"
    
    "github.com/pbednarcik/flexmcp/mcp"
    "github.com/pbednarcik/flexmcp/server"
)

// answerKey identifies the completion across the two round trips.
const answerKey = "answer"

func main() {
    // Create server
    mcpServer := server.NewMCPServer("sampling-example-server", "1.0.0")
    
    // Add sampling tool
    mcpServer.AddTool(mcp.Tool{
        Name:        "ask_llm",
        Description: "Ask the LLM a question using sampling",
        InputSchema: mcp.ToolInputSchema{
            Type: "object",
            Properties: map[string]any{
                "question": map[string]any{
                    "type":        "string",
                    "description": "The question to ask the LLM",
                },
                "system_prompt": map[string]any{
                    "type":        "string",
                    "description": "Optional system prompt",
                },
            },
            Required: []string{"question"},
        },
    }, func(ctx context.Context, request mcp.CallToolRequest) (*mcp.CallToolResult, error) {
        question, err := request.RequireString("question")
        if err != nil {
            return nil, err
        }
        
        // On the retry, return the LLM response
        if result := server.SamplingResponse(request.Params.InputResponses, answerKey); result != nil {
            return &mcp.CallToolResult{
                Content: []mcp.Content{
                    mcp.TextContent{
                        Type: "text",
                        Text: fmt.Sprintf("LLM Response (model: %s): %s",
                            result.Model, mcp.GetTextFromContent(result.Content)),
                    },
                },
            }, nil
        }

        systemPrompt := request.GetString("system_prompt", "You are a helpful assistant.")
        
        // First call: ask the client for a completion
        return server.NewInputRequestBuilder("").
            Sample(answerKey, mcp.CreateMessageParams{
                Messages: []mcp.SamplingMessage{
                    {
                        Role: mcp.RoleUser,
                        Content: mcp.TextContent{
                            Type: "text",
                            Text: question,
                        },
                    },
                },
                SystemPrompt: systemPrompt,
                MaxTokens:    1000,
                Temperature:  0.7,
            }).
            ToolResult(), nil
    })
    
    // Start server
    log.Println("Starting sampling example server...")
    if err := server.ServeStdio(mcpServer); err != nil {
        log.Fatalf("Server error: %v", err)
    }
}
```

## Transport Support

A multi round-trip request travels as the result of the client's own request, so sampling works on every transport a FlexMCP server serves, for a client that has a sampling handler and speaks protocol version 2026-07-28 or later. A client pinned to an earlier version gets `server.ErrInputRequiresModernClient` on every transport.

### STDIO Transport

```go
// Start STDIO server with sampling
server.ServeStdio(mcpServer)
```

### StreamableHTTP Transport

```go
// Start StreamableHTTP server with sampling
httpServer := server.NewStreamableHTTPServer(mcpServer)
httpServer.Start(":8080")
```

Each round trip is a POST of its own, and no connection is held open between them. See [StreamableHTTP sampling](/transports/http#sampling-support).

### In-Process Transport

```go
// Create in-process client with sampling handler
mcpClient, err := client.NewInProcessClientWithOptions(mcpServer,
    client.WithSamplingHandler(samplingHandler),
)
if err != nil {
    log.Fatal(err)
}
```
